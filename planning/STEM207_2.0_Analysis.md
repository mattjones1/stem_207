# STEM 207 2.0: adding depth to the whole application

*Analysis, October 22, 2026. Written for the STEM 207 / STEM Coliseum team deciding the 2.0 scope.*

## Summary

STEM 207 1.x works well inside one browser tab:
- Teachers build Learning Plans, students do activities and send reflections, and teachers mark Pass or Try again.
- The live site already uses a real back end (Supabase): accounts, row-level security, and an event log.

What makes it feel "browser level" is everything around that loop:
- Nothing updates until you reload.
- Nothing reaches you when the tab is closed.
- Nothing works offline.
- Rostering is typed by hand.
- Content lives in code.
- No one above the teacher (a school, a district, a family, STEM Coliseum) can see anything.

**Recommendation for 2.0:** keep the lean classroom loop exactly as it is, and add depth in four places, in this order:
1. **Live and reliable:** real-time updates, an offline-safe outbox, and an installable app.
2. **Classroom connections:** Google Classroom and Clever rostering, plus co-teachers.
3. **Insight:** teacher analytics, standards alignment, and exports.
4. **Organization:** school and district admin, workshop licensing, and a privacy-first family view.

**Also schedule the engineering groundwork:** CI, migrations, and error monitoring. Without it, every one of these is riskier.

## 1. Where 1.x is today

| Area | Today | What it means for users |
|---|---|---|
| Hosting | Static GitHub Pages site. No build step; 36 plain scripts on `window.SE` / `window.STEM`. | Fast and cheap, but every page loads every script. |
| Data | Supabase (Postgres, RLS, RPCs) in cloud mode; localStorage in local mode. Progress is an event log. | Solid model: XP, statuses, and rewards are recalculated from events, so rule changes apply to everyone. |
| Sync | State loads at sign-in and on reload. Writes go through an in-memory outbox that retries when offline. | A teacher doesn't see a new reflection until they reload. If a student closes the tab while offline, queued work is lost. |
| Offline | No service worker. | No school-Wi-Fi resilience, and no "add to home screen". |
| Notifications | None. The Checks badge only updates on navigation. | Teachers have to remember to look. |
| Accounts | Educators: email and password. Students: class code, name, and three secret pictures. | Great for grades 2–8, but every roster is typed (or pasted, as of this round) by hand. |
| Roles | Educator and student (and guest). | No co-teacher, school admin, family, or STEM Coliseum staff view. |
| Content | Activities are JavaScript data files (`activities.js`, `imported.js` via `tools/import_missions.js`). | Every content change is a code change and a deploy. |
| Database changes | `supabase/update-N-*.sql`, run by hand in the SQL Editor (10 so far). | Easy to miss a step; there's no record of which updates have run. |
| Quality | About 20 Playwright test files, run locally with `tests/run.sh`; an in-house accessibility checker. | No CI: nothing stops a broken push from deploying. |
| Insight | Per-class Dashboard, Checks queue, plan Students grid, activity feed. | Good for today, but no trends, no standards view, and no export. |

## 2. Where depth would help

Effort: **S** is days, **M** is 1–3 weeks, **L** is more than a month. Risk covers technical, privacy, and adoption risk.

### A. Live and reliable (platform)

| Idea | User value | Sketch | Effort | Risk |
|---|---|---|---|---|
| **Real-time updates** | Reflections appear in Checks as students send them; a Pass reaches the student's Home right away. | Supabase Realtime on `events` (filtered by class) and `class_messages`. Re-render only the part that changed (badge, feed, Up next). | M | Low. RLS already scopes the rows. |
| **Durable outbox** | No lost work on bad Wi-Fi or a closed laptop lid. | Persist the outbox in IndexedDB and replay it at the next load. Events already have client ids, so replays are safe. | S | Low |
| **Installable app (PWA)** | An icon on Chromebooks and iPads; opens fast; activity pages and labs work offline. | Web app manifest plus a service worker that caches the app shell, labs, and activity data. Network-first for data. | M | Medium: cache invalidation on deploy. |
| **Teacher notifications** | "3 reflections waiting" without checking the site. | A daily email digest first (Supabase Edge Function plus cron); web push later, opt-in. | M | Medium: email deliverability, opt-in rules. |
| **Class display mode** | Run a lab or show the class journey on the projector. | A read-only presentation route per class. (The old Projector button was removed for being device-wide.) | S | Low |

### B. Classroom connections

| Idea | User value | Sketch | Effort | Risk |
|---|---|---|---|---|
| **Google Classroom / Clever rostering** | No typing names; classes stay in sync. | OAuth for educators; import rosters as display name (first name and last initial) plus picture codes. Store no emails for students. | L | High. Privacy review and app verification needed; keep picture sign-in for grades 2–5. |
| **Teacher SSO** (Google, Microsoft) | One less password. | Supabase Auth providers. | S | Low |
| **Co-teachers and shared plans** | A STEM coach and a classroom teacher run one class; a school shares a plan library. | A `class_members` table with roles; plans shared by link or by school. RLS updates. | M | Medium: RLS complexity. |
| **Due dates and scheduling on plans** | "Session 2 is Thursday." Pairs naturally with workshops. | Optional dates per plan and per workshop session, shown on Home's Up next. | S | Low |
| **LTI 1.3** (Canvas, Schoology) | Launch STEM 207 from an LMS and send grades back. | Later, if districts ask. | L | High |

### C. Content depth

| Idea | User value | Sketch | Effort | Risk |
|---|---|---|---|---|
| **Content authoring (CMS)** | Curriculum staff add and edit activities without a developer. | Move activities to a `content` table with versions and `pub` states (the model already exists in `SE.content`), plus an editor for staff. Keep the import tool for bulk loads. | L | Medium: moves the source of truth. |
| **Standards alignment** | Teachers and districts see which standards a plan covers. | Tag activities with CSTA, NGSS, and Maine Learning Results. A plan page shows its coverage; a filter by standard. | M | Low. Needs curriculum review time. |
| **3D Printing goes live** | The seventh category gets real activities and workshop add-ons. | Replace the five placeholders. Pair with a printer-queue or file-hand-in step (an upload, reviewed by the teacher). | M | Medium: file storage and moderation. |
| **Moxie reaches pilot** | The ESP32 pathway becomes teachable; the Robots workshop gets its capstone. | Already outlined; needs reuse permissions, hardware validation, and pilot timing. | M | Medium: permissions are the blocker. |
| **Student uploads** (photo of a build, a Scratch link) | Richer evidence than text for maker activities. | Supabase Storage with teacher-only visibility. Hands and objects only; no faces, per the camera rule. | M | High: moderation and privacy. |

### D. Insight

| Idea | User value | Sketch | Effort | Risk |
|---|---|---|---|---|
| **Teacher analytics** | Spot who's stuck and which activities cause Try agains. | From the event log: time from send to pass, try-again rate per activity, a concept heatmap per class. | M | Low |
| **Exports** | Report cards, grant reports. | CSV per class or plan: statuses and passes. No reflections by default. | S | Low |
| **Family view** | Families see progress at home. | A read-only link per student, revocable by the teacher. Shows passes, patches, and the harbor; no reflections or notes. | M | Medium: consent and privacy design. |
| **Program reporting for STEM Coliseum** | Show impact across workshops and schools. | Aggregated, de-identified counts only. | M | Medium |

### E. Organization and business

| Idea | User value | Sketch | Effort | Risk |
|---|---|---|---|---|
| **School and district admin** | One place to add teachers, see usage, and manage licenses. | An `organizations` table, admin role, and invite flow; RLS by organization. | L | Medium |
| **Workshop packaging** | Sell and run the three workshops (Maine Tech Sampler, Robots & Smart Machines, Coast to Katahdin) as products. | Workshops become a first-class type: dates, facilitator, materials list, printable facilitator guide, post-workshop survey. | M | Low |
| **Facilitator mode** | A STEM Coliseum instructor runs a workshop with a pop-up class. | Temporary classes that expire, with batch login cards (the new Add students dialog is the start). | S | Low |

### F. Trust: privacy, safety, accessibility

| Idea | Why | Sketch | Effort |
|---|---|---|---|
| **Privacy posture** | Schools will ask before 2.0 adoption. | A written COPPA, FERPA, and Maine student data privacy position; data retention and deletion rules; a data processing agreement template. | M |
| **Data retention tools** | "Delete everything for this class at year end." | Scheduled archive and delete; exports first. | S |
| **Audit log for teachers' actions** | Disputes ("I passed that"). | The event log already records teacher events; add a teacher-facing history view. | S |
| **Accessibility in CI** | Keep 0 findings as the app grows. | Run the in-house checker plus axe-core in GitHub Actions. | S |

### G. Engineering groundwork

| Idea | Why | Sketch | Effort |
|---|---|---|---|
| **CI** | Stop broken pushes from deploying. | GitHub Actions: `node --check`, `tests/run.sh all` with Postgres, accessibility, then deploy Pages only if green. | S |
| **Migrations** | Replace "run update-N by hand". | Supabase CLI migrations with a version table; one command per environment. | S |
| **Error monitoring** | Know when a lab breaks on a Chromebook. | A small error reporter (no personal data) to a hosted service or a Supabase table. | S |
| **Modules, still no framework** | 36 global scripts are getting hard to change safely. | Native ES modules with import maps, no bundler. Split views by route and load labs on demand. | M |
| **Staging site** | Try changes before families and schools see them. | A second Pages site plus a Supabase branch. | S |

## 3. Recommended 2.0 scope

**Must (2.0):**
- Groundwork: CI, migrations, error monitoring, and a staging site.
- Real-time updates and the durable outbox.
- The PWA (installable, with an offline app shell and labs).
- Teacher SSO.
- Due dates on plans and workshop sessions.
- Exports.
- A written privacy posture with data retention tools.
- Workshop packaging and facilitator mode, which tie directly to STEM Coliseum's business.

**Should (2.x):**
- Google Classroom / Clever rostering.
- Co-teachers and shared plans.
- Teacher analytics.
- Standards alignment.
- The teacher email digest.
- 3D Printing live.

**Later:**
- The content CMS.
- School and district admin.
- The family view.
- Student uploads.
- LTI.
- Moxie (gated on permissions, not engineering).

## 4. Phased roadmap

| Phase | Theme | Contents | Rough size |
|---|---|---|---|
| 0 | Groundwork | CI, migrations, staging, error monitoring | 1–2 weeks |
| 1 | Live and reliable | Realtime, durable outbox, PWA, teacher SSO | 3–5 weeks |
| 2 | Workshops as a product | Dates on plans and sessions, facilitator mode, printable facilitator guides, exports | 3–4 weeks |
| 3 | Classroom connections | Classroom / Clever rostering (after the privacy review), co-teachers, shared plans | 5–8 weeks |
| 4 | Insight | Analytics, standards, digest | 4–6 weeks |

## 5. Open questions for the team

1. Who is the 2.0 buyer: individual teachers, schools, districts, or STEM Coliseum workshops? This decides whether admin and licensing move up.
2. Which rostering do Maine partner schools use most: Google Classroom, Clever, or ClassLink?
3. Is a family view wanted, and with what consent model?
4. Which standards matter most to partners: CSTA, NGSS, or Maine Learning Results? **Decided October 28, 2026: CSTA + NGSS** (Maine's science standards are NGSS-based). All 56 activities are tagged (`assets/js/data/standards.js`); plan and template pages show their coverage, and library search finds activities by code.
5. What's the plan and timeline for 3D Printing content and Moxie reuse permissions?
6. Is there budget for a hosted error and email service, or should everything stay on Supabase?
7. Do workshops need payment and registration in the app, or does STEM Coliseum handle that elsewhere?
