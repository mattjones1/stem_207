# STEM 207 — Coding Categories and Progression

## Scope

This guidance applies specifically to organizing and developing STEM 207's **coding categories**, their missions, and the coding pathways educators build from them.

**Keep the humanity in technology.**

STEM 207 serves grades 2–8. Coding experiences should build curiosity, confidence, creativity, and the ability to solve problems for people.

## Meaning of coding categories

Retain **Coding & Computer Science** as the existing top-level Category unless the user explicitly approves changing the site's taxonomy.

Within it, introduce the coding categories below as proposed browsing groups or subcategories. A coding category organizes related content. A coding pathway sequences selected missions toward a specific outcome. Keep these concepts separate.

A mission may appear in more than one coding group through references or tags. Keep one canonical mission record. Do not duplicate content to populate several screens.

These are planning recommendations. Their availability must be established by reviewing actual mission content, not by creating empty public offerings.

These groups intentionally combine an entry route, coding environments, and applications because students browse by different interests. Keep **concept**, **tool/language**, and **category** as separate metadata so the overlap remains manageable. Minecraft, Roblox, 3D game engines, Java, and C# appear in the reference graphic. Treat them as possible future additions, not required launch categories. Add a dedicated group only when there is a supported platform, enough reviewed content, and a clear learning purpose. Do not equate 3D games with 3D printing.

## Progression within coding categories

Use increasing independence and demonstrated skill to describe progression. Beginner, Intermediate, and Advanced may be used if compatible with current labels. These describe readiness within a category, not a student's overall ability or a fixed age band.

| Stage | Learner behavior | Evidence |
| --- | --- | --- |
| Beginner | Predict, follow, explain, and change a short program with support | Working change plus a simple explanation |
| Intermediate | Combine concepts, make design choices, and debug with decreasing support | Functional project, test observations, and explanation of a fix |
| Advanced | Plan for an audience or problem, structure a larger program, test, and refine | Original project, feedback, revision, and explanation of tradeoffs |

Do not invent three levels of content for every category. Show only reviewed offerings and mark actual gaps in the internal plan. A student can be experienced in Scratch and new to Python. Use an entry check and a concept bridge instead of requiring every beginner activity again.

Suggested bridges to evaluate include block loops to Python loops, Scratch variables to text variables, input events to interactive web behavior, and conditions to sensor decisions. These are instructional connections to develop, not claims of existing missions.

## Mission content requirements

Each publishable coding mission needs:

- One clear learning objective and a student-friendly purpose.
- Prerequisite skills and readiness guidance, with grades as guidance rather than mastery claims.
- A usable coding platform or self-contained environment, including account, installation, device, and cost requirements where relevant.
- A realistic time estimate, starting project or code, and manageable instructions.
- A prediction or design choice, an opportunity to test, and useful debugging support.
- A concrete deliverable and a short explanation or demonstration that reveals understanding.
- Instructor notes, an optional extension, and accessible instructions.

Prefer concepts that transfer between tools. Do not define success as following clicks, copying code, opening a page, or accumulating badges. Use Maine settings when they add meaning, while allowing students to choose their own themes.

## Educator pathway composition

Educators should be able to choose a learning goal, select missions from multiple coding categories, order them, check prerequisites and tools, and define the final body of work.

A game pathway might connect foundations, block coding, and game design. A later pathway might bridge that knowledge into Python. These are structural examples; do not assign specific missions until their content has been reviewed.

Each pathway should explain:

1. What students will be able to do.
2. Why the selected missions belong together.
3. What prior skills and resources they need.
4. What evidence marks progress.
5. What students will create, test, improve, and explain at the end.

Reference canonical missions. Store educator-specific instructions on the pathway step. Preserve assigned content versions so later curriculum edits do not silently change expectations for current learners.

## Coding discovery and storytelling

Propose a coding landing experience with category descriptions, available missions, readiness guidance, tool filters, and next-step suggestions. Separate **browse a coding category** from **follow a coding pathway**.

Every category description should answer: “What can I make here?” and “What coding skills will I practice?” Show available work accurately. Do not present draft categories as complete courses or display fabricated student projects.

Showcase approved student work with the goal, code concepts, testing, and improvement. Keep student evidence private by default and use existing educator review and consent controls for public examples.

## Acceptance criteria for later authorized implementation

- Coding categories help learners find relevant missions without replacing the existing coding pathway.
- Existing mission IDs, routes, and progress remain intact.
- Every mapping is based on reviewed content; overlap uses references rather than duplicate lessons.
- Tools and coding concepts are recorded separately.
- Readiness and next steps are understandable, with no automatic age-to-mastery assumptions.
- Empty or draft offerings are not advertised as available curriculum.
- Educator-created pathways can connect coding groups toward a clear deliverable.
- The content structure supports future missions and tracks their revisions.
- Other STEM 207 Categories and the separate Moxie pathway remain unaffected.
